# End-to-end proof, 2026-10-24

The ported runtime (`ingestor-runtime-0.1.0-all.jar`) run against an isolated local platform (`fcdev`
built from the working tree). No secret values appear here; the platform and runtime credentials were
generated for the run and the instance was stopped (its data stays in the scratchpad).

## Setup

```
go build -o e2e/fcdev ./cmd/fcdev
FC_INGESTION_LEASE_SECONDS=20 fcdev start --api-port 18080 --embedded-db-port 25432 --embedded-db-path r2/pg \
  --metrics-port 19090 --functions-port 18095 --functions-public-port 18096 --pid-file r2/fcdev.pid \
  --mcp=false --outbox=false --router=false --scheduler=false      # router/scheduler off: jobs stay PENDING
```

Login `POST /auth/login` with the dev admin (cookie sessions, `Origin` = base URL). Then:

| What | Call |
|---|---|
| client `acme` | `POST /api/clients` |
| INTEGRATION application `feeds` | `POST /api/applications {"code":"feeds","type":"INTEGRATION"}` |
| pool `acme-pool` | `POST /api/dispatch-pools` |
| runtime service account | `POST /api/applications/{id}/provision-service-account` (code `app:feeds`, OAuth client returned once) |
| its role | `PUT /api/service-accounts/{id}/roles {"roles":["platform:ingestion-runtime"]}` |
| secret `orders-token` | `PUT /api/config/feeds/secrets/orders-token?clientId=<acme>` `{"value":...,"valueType":"SECRET"}` |
| connection `feeds-conn` (signed by `app:feeds`) | `POST /api/connections` |
| ingestions | `fcdev ingest apply defs --platform http://127.0.0.1:18080` (folder: `orders-http`, `orders-signed` (with `connection: feeds-conn`), `gen-feed`, later `tick-feed`) |

Runtime: `java -jar ...-all.jar` from a directory holding `config/application.yaml`, with
`FLOWCATALYST_BASE_URL`, `FLOWCATALYST_CLIENT_ID`/`_SECRET` (the provisioned account), `INGEST_RUNTIME_ID`,
`HTTP_PORT=18091`, `INGEST_POLL_INTERVAL=PT10S`, `INGEST_EXTENSIONS_DIR` with the generator jar.

### What the runtime's account needs (answer to "find out and report")

> **Superseded (2026-10-24, same day):** the runtime routes are now platform-wide. The role
> `platform:ingestion-runtime` reaches every client and application whatever way the account was provisioned, so the
> account-binding finding below no longer applies. It is kept as the record of what the first run showed.

The role `platform:ingestion-runtime` alone is enough. The account is bound to the application `feeds`, which
makes it application-scoped, and the poll then lists only ingestions of `feeds` (`ingestion.ListReach`). Client
reach is not an issue: a service account's principal is anchor-tier, so it reaches every client although
`clientIds` is empty. So: the role, and a service account bound to the owning application of every ingestion it
should run; an account bound to no application (an all-applications account) reaches every application. The
role assignment is a replace: assigning it removed the default `platform:application-service`, which the runtime
does not need.

## Defects found

1. **The runtime could not read any platform answer (fixed).** The first poll against the real platform logged
   `could not ask the platform what to run ... cannot be read`, forever. Cause: `PlatformApi` read answers with the
   framework's strict mapper (`FAIL_ON_UNKNOWN_PROPERTIES`), and every huma answer carries a `$schema` member.
   The fake platform in the tests never sent it. Fix: answers are read with a lenient mapper (also right for the
   contract's "additive changes do not bump it"). Test `PlatformApiTest.aPollAnswerWithMembersTheRuntimeDoesNotKnowIsStillRead`
   fails without the fix (`the platform's list of ingestions cannot be read`) and passes with it. Full module: 104 run, 0 failed, 20 skipped (Docker).
2. **The jar does not start without `config/application.yaml` in its working directory** (`flowcatalyst.application: required`).
   The image has the file. Not a code change; README now says so.

## Proofs

1. **Poll and route states.** After the fix the runtime logged `started ingestion ...`; `ing_route_states` shows
   `STARTED` per (ingestion, runtime), and `ing_runtimes` holds the runtime with the `generator` kind and its settings
   schema (`GET /api/ingestion-source-kinds` lists `generator`).
2. **HTTP push becomes a dispatch job.** `POST :18091/ingest/acme/orders-http` with `Authorization: Bearer <secret>` answered
   `202 {"accepted":true}`. `msg_dispatch_jobs` row: `code acme:order:received:v1`, `source ingestion:feeds:orders-http`,
   `target_url https://hooks.example.com/orders`, `dispatch_pool_id` = `acme-pool`, `client_id` = acme, payload as sent,
   `application/json`, metadata `ingestionId` + `runtimeId`, status PENDING. For `orders-signed` the row also holds
   `connection_id` = `feeds-conn` and `service_account_id` = `app:feeds`.
3. **Wrong or missing token** answers `401 UNAUTHENTICATED`, no job. The secret was revealed through the runtime secrets
   endpoint; `aud_logs` has one `SECRET_REVEALED` row per ingestion (entity `PLATFORM_CONFIG`, principal = the runtime's
   account, operation json names section `secrets`, property `orders-token`, `ingestionCode`, `runtimeId`). The 1-minute cache
   means the later requests wrote no further rows, and the wrong token wrote none.
4. **Generator** (`every PT10S`, `count 2`): two jobs every 10 s (`source ingestion:feeds:gen-feed`), seen at 16:56:50, :57:00, :57:10 ...
5. **Pause.** `POST /api/ingestions/{id}/pause` at 16:58:51; at the next poll the log shows `Stopped ... Shutdown ... stopped ingestion`
   and a push answers `404 no such ingestion`. Resume brought it back.
6. **Test connection.** `POST /api/ingestion-tests {"ingestionId":...}`: generator -> `DONE`, `NOT_SUPPORTED` ("offers no test");
   http -> `DONE`, `NOT_SUPPORTED`. An unsaved api-poll definition against the platform's `/health`
   -> `DONE`, `RESULTS`, steps `GET /health answered 200, 32 B`, `Results: $.status is UP.`, `The split makes 1 record`.
   Each came back within one poll.
7. **Lease move.** Lease acquired by `r2-a`, expiring 17:01:30. `r2-a` killed by its pid at 17:01:15; `r2-b` started; at 17:01:36
   (its first poll after expiry) the lease row became `r2-b` (20 s lease, renewed every poll) and `gen-feed` jobs continued from
   17:01:37 with `runtimeId r2-b`. The shared http routes ran on both.
8. **Extensions.** A tiny extension (`tick`, the generator source renamed to package `io.example.tick`, built with `javac`
   against the fat jar) dropped into `INGEST_EXTENSIONS_DIR`: log `extensions: generator, tick`; `GET /api/ingestion-source-kinds`
   lists `tick`; `fcdev ingest apply` of `kind: tick` created `tick-feed`; jobs `{"n":1,...}`, `{"n":2,...}` every 10 s.
   Refusals (exit 1, start aborted):
   - API 2: `extension ingestor-extension-tick-v2.jar was built for extension API 2; this runtime speaks 1. Rebuild it against ingestor-extension 1.x`
   - no attribute: `extension ingestor-extension-tick-nomanifest.jar does not declare the extension API it was built against: its manifest needs Ingestor-Extens...`

## Observations (platform or runtime, not fixed)

- A runtime that is stopped leaves its `ing_route_states` rows (`STARTED`) behind, and a paused ingestion keeps its last
  `STARTED` row; nothing reports `STOPPED`. Pages that read these rows should key on `ing_runtimes.last_seen_at` and the
  ingestion's status. Minimal repro: stop a runtime, query `ing_route_states`.
- An HTTP push's `X-Correlation-Id` is echoed in the response but the job's `correlation_id` is the runtime's own
  `<ingestion>:<run>-<n>`; the caller's id is not carried. Decide whether a header should become `correlationId`.
- `fcdev` was built from a tree with other agents' uncommitted changes; nothing in the results depended on them.

## Stopped

`r2-b` and `fcdev` stopped by pid (clean shutdown); `r2-a` and the probe runtimes were already stopped. Nothing else was removed.
